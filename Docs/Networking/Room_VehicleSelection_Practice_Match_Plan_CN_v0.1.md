## 1. 用户提出的目标

街机式等待进入界面 → 建立／加入房间 → 选择已有车辆 → 进入可驾驶练习场等待 → Host开始 → 全体进入正式关卡。素材先用占位，流程和数据归属按后续正式开发建设；沿用四机有线Listen Server，不据此扩建匹配服务或完整比赛框架。

## 2. 建议的玩家流程

| 步骤 | 玩家所见与行为 | 服务器负责的条件 |
|---|---|---|
| 本地入口 | 按键／Start进入操作，创建房间或输入Host IPv4加入，显示连接中／失败原因 | 连接成功后才占房间席位；入口画面本身不代表已经联网 |
| 房间内选车 | 显示四人席位、车型、选车／确认状态，键鼠与手柄均可操作 | 验证车型来自允许目录、配置有效；确认后记录稳定VehicleId |
| 确认并练习 | 服务器以所选车辆生成并Possess；玩家在场内练习，同时看到队友选车进度与Host开始入口 | 成功出生并完成车辆／GAS／输入就绪后，才算可参加；房间仍可接收剩余席位 |
| Host开始 | 锁定本次参与名单及车型，禁用再选车／加入，显示转场中 | 检查人数、全体确认、车型有效及目标地图；只接收当前Host一次有效请求 |
| 正式地图加载 | 显示每人载入／准备情况，加载快的人等待 | 服务器按同一名单生成正式车辆，确认地图、Avatar／ASC等必要状态就绪；不能只按连接人数或固定等待几秒开赛 |
| 倒计时／比赛 | 全体就绪后共用服务器开始时刻，倒计时结束开放正式操作 | 倒计时前冻结驾驶／技能／伤害等规则，不冻结为UI动画；慢机器有超时与退出策略 |
| 后续返回 | 未来结算后回房间可保留车型，或离房回入口 | 本轮可先预留返回房间入口与清理契约；不自动扩建完整淘汰／观战／胜负系统 |

“选车→练习”建议作为**同一联机房间地图内的每玩家流程**：未确认者显示选车UI，不生成可驾驶车；已确认者进入练习。无需每确认一人就切地图，也不必等最后一人才能练习。可暂用MVPB_NetTest关卡承载房间，建议由团队手工复制房间用途版本或配置专用房间GameMode，保留原网络回归地图的既有行为。

Host自身也是这四个席位中的一名玩家。以后若有独立展出控制端，另作规则讨论，不在本方案隐含加入第五台设备。

## 3. 建议默认规则，尚待确认

1. **允许重复选同车型。** 当前两类车支持四人；通过玩家颜色／编号区分归属，不能只靠车型区分敌我。
2. **确认选车同时表示同意Host开始。** 确认后能练习，无需再加第二个“准备”按钮。开始前允许取消确认并返回选车；销毁旧Avatar、释放球、清理旧车作用域状态后再生成新车，不做行驶中直接替换配置。
3. **房间／练习期间允许加入，Host开始锁定名单后禁止中途加入。** 房间最多四人；正式展出建议四人开始，开发模式允许一人练习与走完整转场，人数由规则配置，不写死在Widget。
4. **练习保留碰撞、控球、发射、冲击和技能；首版建议不扣HP、不淘汰。** 不计算正式时间／成绩；进入正式关卡时满血、技能可用，所有练习Buff／Debuff、冷却、持球和速度均重置。若希望练习也扣血，需要另定零HP恢复方式，本条不是已确认选择。
5. **地图首版由Host选择或使用配置默认地图。** 玩家投票／随机轮换后续扩展；目录只允许可发布的地图与车型，确保软引用资源进入打包，不接受任意客户端类／地图路径。
6. **暂不做重连与主机迁移。** Client在房间离开则清席位、球权和Avatar；Host退出则全体回入口并说明原因。载入失败／超时首版建议明确报错并取消本次开赛，恢复房间；具体超时和失败恢复路径须在施工规格中明确并实测。

## 4. 正式结构与现有实现差距

- 现有`HALNetworkGameInstance`已实现Host／IPv4 Join、入口Widget和连接错误文本，可继续用；当前Host直接打开NetTest，不存在独立房间到正式地图转场。
- 当前`HALMatchGameMode`以唯一DefaultPawnClass出生，不能按每位玩家车型选择。建议新增一个小型车型目录：稳定VehicleId映射至车辆BP、显示名／图标／预览资源。BP继续引用已有VehicleDefinition，不在UI复制整份物理／技能参数。服务器验证ID后决定出生类；后续新增车型主要是目录与资产配置。
- `PlayerState`保存选车确认、席位等玩家信息，继续作为ASC Owner；`GameState`复制房间阶段／名单和开赛状态；服务器GameMode决定接纳、选车、生车与转场。GameInstance只管本地偏好、连接及UI协调，不能代替复制的服务器房间状态。Widget只提交请求、显示结果。
- 房间与正式关卡可分别使用小型GameMode／GameState，复用共享身份、车型目录、出生及生命周期逻辑。不要把所有业务塞入GameInstance或Level Blueprint，也不必把本地入口、每玩家选车和整局比赛塞进同一个阶段枚举。
- 现有`WaitingForPlayers／Playing`不足以表达练习、转场、加载与倒计时。技能、相机、电墙、自救等多处直接检查Playing，必须梳理成少量一致的权限查询，确保练习可操作但不进入正式计分／伤害规则，加载和倒计时不误开放。单纯增加几个枚举值会漏掉这些条件。
- **GAS重置是本阶段必做内容。** 当前`InitializeHealth／InitializeCombat／InitializeImpact`分别有一次初始化保护，重复绑定不会重读车型数值；Avatar切换只会按已有作用域清理一部分效果，不能当作“完整新一局重置”。需要区分重复绑定、新车型初始化与新一局重置；审计技能授予来源／旧车能力移除、属性种子、冷却、区域效果和预测缓存，避免换车继续用旧HP／攻击／冲击配置。不要简单在每次Possess或每次OnRep时强制回血／清技能。
- 练习场到正式地图由服务器统一发起`ServerTravel`，建议优先采用并验证Seamless Travel；玩家身份／车型明确保留或复制，Pawn、球和练习效果按新局重新建立。Seamless不代表没有加载或会自动正确保留所有ASC状态。[Epic官方转场说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/travelling-in-multiplayer-in-unreal-engine)。

## 5. 容易遗漏、应进入施工规格的逻辑

- 同时点选／反复确认／取消、开始请求重复到达、加入和开赛同帧的接纳判定，均由服务器串行决定。
- 车型无效、配置未Ready或出生被挡时，不标记就绪；UI显示原因，提供重试／换车，而不是进入游戏后发现无法驾驶。
- 稳定席位与颜色保持；不把跨新连接也有效的身份保证建立在本局PlayerId或Actor名上。当前无重连承诺。
- 全员载入检查按本次开局名单及开局序号，过期就绪消息不能启动下一局；检查必要的客户端Pawn引用／输入与服务器ASC初始化，载入超时不永久卡房间。
- 从选车UI切驾驶、打开暂停菜单、返回选车、转场和重新Possess时，明确焦点／手柄导航／光标／IMC清理；不能因UI吞输入造成“车坏了”。
- 跨图清除旧HUD、相机目标和网络物理缓存；正式出生位置按关卡PlayerStart重新选择，练习球不带入正式场。
- 断线、Host退出、目标地图缺失与载入失败的回入口／回房间路径需单独验证，不能只提供一条向前流程。
- 展出反复游玩需要回房间／重新准备的闭环；即使正式比赛结束尚未实现，本轮也应能用开发入口验证连续两次开局不继承上一局状态。

## 6. 建议分段施工及验收

1. **流程规格与数据边界：** 确认第3节规则；确定房间／正式地图、车型目录、每玩家确认状态、权限表、名单锁定及重置契约。先不制作精细UI。
2. **灰盒房间＋按人选车／练习：** 复用Host／Join，先用简单控件把两类车辆选车、确认、各自出生、取消重选和新玩家加入跑通；重点验证不同基础属性不会沿用、无重复ASC授予／旧球权。
3. **真实跨图纵切：** 先验证一Host一Client的ServerTravel、车型保留、状态清理、载入屏障、倒计时及失败路径，再扩至四机。只靠假计时页面跳转不算通过。
4. **入口与选车表现：** 街机待机页、手柄／键鼠焦点、四席位展示、车型预览、连接／出生／加载错误反馈；表现替换不影响目录ID和服务器规则。
5. **退出返回与循环回归：** 确认取消／离房／Host关闭／超时，连续两次开局，开发单人模式及四台真实电脑。打包验证地图与车型Cook引用。结算和正式淘汰规则另列后续阶段。

本草案没有开展上述施工；确认规则后再拆成单独可编译、可验收的小步。
