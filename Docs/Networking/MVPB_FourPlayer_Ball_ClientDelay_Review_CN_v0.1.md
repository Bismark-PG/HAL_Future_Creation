## 3. 按链路拆解

### 3.1 捕获与持球：本地车即时预测，球继续等待服务器运动

`BallControlComponent::BeginPlay/EvaluateBallControl`只在服务器运行选球定时器；`AcquireBall`提交Controlled并建立实际Chaos约束。客户端`BasicBallActor::ApplyReplicatedPresentation`只保留球刚体、忽略碰撞响应并关重力，继续消费服务器复制／PI，不建立本地吸球或跟随约束，也没有将球每帧移到本地控制点。

因此客户端自己的车通过Resimulation立即消费输入，球仍表现服务器已产生的运动。加速／转向／刚捕获时，这两者暂时不在同一时间线上；观感可能是球晚吸入、拖在车后或追赶。观察别人的车和球时，两者虽然都可用PI，但仍是独立Actor、独立更新和纠偏，不能假定每帧完全同步到达。该机制同时涉及用户报告的两种场景，匹配程度高；本次没有动态录制，不能量化它是否占主导。

### 3.2 PI不是原样播放：更新越稀疏，纠偏可能越慢

本机UE的`PhysicsReplication.cpp`中，PI根据`AverageReceiveInterval`计算插值时长，位置纠偏时长又考虑该更新间隔、RTT及最小纠偏时间。四人时若Host Game帧慢、网络调度／带宽竞争或链路抖动导致有效更新变稀，显示修正可能随之拉长。即使球目标频率是100，也不能突破主机实际处理／发送和连接预算。

这是源码可证明的放大机制，**尚未测得本次四人存在多少卡帧、丢包或排队**。学校有线只说明接入介质，不能替代实际Ping／抖动测量。当前也没有证据证明球DA被人为设了过大的额外平滑值；其PI覆盖仍是关闭的。

### 3.3 发射：预测了车的反馈，没有预测真实球的离手轨迹

`TestVehiclePawn::OnLaunchStarted`提交Reliable的ServerRequestLaunch；服务器核对当前球权与状态序号，调用`LaunchHeldBall → LaunchFromControl`设置球初速度。客户端当前即时预测的是车辆后坐／视觉回弹，不是球初速度。`ClientLaunchResult`也只确认车辆表现，不直接将球切到本地发射轨迹；球仍依靠自身状态／刚体复制到达并由PI表现。

因此客户端发射可包含输入上行、服务器处理、球运动下行及PI响应；Host本地直接执行权威发射，体验天然不同。车辆Reliable回执、球RepState与刚体状态也不是同一份原子运动快照；`ForceNetUpdate`能提示尽快更新，不能保证同一帧到达或消除网络时延。球专用DA中的Event Scheduling Min Delay=0.3秒并不是此处普通球发射的固定等待计时器，不能直接把它认作300ms根因。

### 3.4 刚获得球立即按发射，还可能是拒绝而非晚执行

客户端只用已观察到的唯一Controlled球填写ExpectedBallStateSequence；未收到球权快照时可能填0，快照过期时也可能不匹配服务器当前序号。服务器会拒绝，客户端需要后续再次按键，主观上可能像发射延迟。这是代码中确实存在的边界，但本机实战日志未开VehicleNetLog，不能认定本次实际发生。不能为改善手感直接删除服务器球权校验。

## 4. 建议后续顺序（尚未施工）

1. **先做同设备／同版本的两人→四人对照采样。** 保持球、车参数，核对四台的提交、引擎补丁及保存配置。Host和至少一台客户端开启`hal.BallNetLog 1`、`hal.VehicleNetLog 1`；显示`stat unit`、`stat net`，短录15～30秒：主机持球直走／急转／发射，再客户端做同样动作，另单测刚捕获立即发射。记录Ping、丢包、收发速率及Host Game／Draw／GPU时间，区分整个球轨迹滞后与短促吸入／离手切换慢。结束关闭日志及统计。
2. **对齐证据再区分瓶颈。** 用Ball StateSequence、LaunchSequence、服务器接受／拒绝和客户端收到状态的记录定位迟到环节。不同电脑UTC时间未同步时，不能直接将两机日志时间相减当精确时延；配合同步录像／网络采样。现有HALNetMetrics只有车辆帧和重模拟计数，不包含球包间隔或Ping；如需精确收包间隔／状态年龄，应另授权增加可关闭诊断，不能假称现有日志已测得。
3. **确认Host或实际发送间隔问题时，先处理其瓶颈。** 看Host帧时间、后台降频、未关闭网络模拟及实际连接预算；不要先把100调得更高，或以降低球质量／增大约束力补偿网络延迟。
4. **低RTT且Host稳定仍慢时，再评估球专用PI及状态切换的调整。** 当前已有球DA，可以独立小步调纠偏／插值并A/B；需要同时验证抖动、碰撞收敛和状态切换，不能直接关闭全部平滑。
5. **若仍达不到展出手感，再单列可回滚／可纠正的球表现预测方案。** 重点讨论本地持球与离手即时反馈、权威确认／拒绝及切换交接；球权、伤害与碰撞裁决继续服务器统一。不得恢复旧的客户端独立固定吸入曲线、直接把所有球改Resimulation，或在本轮检查中顺手实现另一套规则。

这次四人反馈是有效缺陷／待优化项，不是四机验收通过。完整F4／VP复杂组合／四台有线PC长时验证仍未完成；本轮不扩展完整比赛、GAS或技能框架。

## 5. 转弯／速度变化时滞后的定向方案（讨论，尚未授权施工）

用户进一步说明延迟基本出现在车辆转弯、速度变化时，认为车／球时间线不同很可能是主因，并询问解决办法。该症状强化了第3.1节的候选解释，但未新增Host帧率、Ping或球包间隔证据。本节是设计建议，不代表已经施工或验证。

### 5.1 推荐先做Controlled球的相对车辆表现

持球视觉由“独立追赶服务器球的世界位置”调整为：**客户端当前持有车辆的显示变换 × 服务器同步的球相对该车的变换**。

- 服务器继续用现有Chaos约束决定真实球的位置、吸入、球权、碰撞与伤害。额外提供的是表现用相对位置／姿态快照，不成为第二套球权或权威规则。
- 相对变换必须来自同一物理帧的车和球，携带当前StateSequence、Holder身份及帧／时间信息；不能直接拼接两个不同步的GT Transform计算偏移。复制采用有界频率／变化阈值，实施规格再确定，不发逐渲染帧RPC。
- 客户端让球的可见网格基于持有车辆当前显示姿态，平滑消费权威相对偏移。自己的车使用预测／纠正后的姿态，远端车使用其插值显示姿态；转弯和加速的共同车体变换即时一致，服务器约束形成的真实相对滞后仍被保留。
- 球物理根继续既有PI及状态切换，Controlled时保持物理状态、Ignore响应及关闭本地重力。只改无碰撞的VisualMesh表现，不把刚体直接移到本地车头，也不新增客户端约束或玩法裁决。
- 吸入相对运动继续来自服务器约束结果；不恢复旧版独立固定0.18秒客户端吸入曲线。两端数据同源，但预测车的显示时间不同，不能承诺世界轨迹逐帧／逐像素一致。剩余相对偏移的迟到与真实物理惯性仍须测量。

### 5.2 状态交接是同一步的必做内容

进入Controlled时保留上一可见世界姿态，连续交接至有效相对快照，避免捕获瞬移；不能因Holder尚未解析就强行套用变换。旧StateSequence／旧Holder数据应丢弃。脱球、发射、持有者退出时撤销相对表现，并将当前可见姿态连续交给相应的权威球运动；处理球状态与刚体数据分批到达，不能突然显示物理根的较旧位置。等待／外推必须有界，异常时返回原PI显示。球面滚动、视觉重配及销毁也要清理，避免重现球不动或切状态卡住。

建议以可关闭的表现配置／诊断做A/B：持球直走、加减速、急转／倒车，主机／客户端互换、观察远端持球；覆盖吸入中立即发射／脱球、贴墙、球权变化、异常引用和网络抖动。对比车球相对显示误差、状态交接跳变，以及权威球位置／碰撞／伤害是否保持。四机性能与网络采样继续，不能只凭新视觉看起来跟车就关闭原延迟问题。

### 5.3 发射即时表现分开处理

本步主要针对持球吸入／跟随的转向和速度变化错位。实际发射仍需服务器确认，往返等待不会因相对表现自动消失；先确保离手交接连续，再依据实测决定是否单列“按键后球的非权威视觉发射预测”，用LaunchSequence确认／拒绝并回收校正，真实球权／碰撞／命中继续由服务器决定。当前不直接承诺全球Resimulation或新玩法模拟框架。

推荐施工边界为：**最小诊断／A-B基线 → Controlled相对表现＋完整状态交接 → 团队双端／四机复测 → 决定发射视觉预测是否需要另开小步。** 具体复制格式、采样时机、误差阈值和开关在施工规格中定稿；本轮只有说明更新，无代码、资产、编译或新测试。
