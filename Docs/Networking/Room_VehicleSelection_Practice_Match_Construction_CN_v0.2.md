## 1. 用户已确认的六项规则

| 编号 | 确认规则 | 实现含义 |
|---|---|---|
| R1 | 允许重复选择同车型，用颜色／编号区分 | 四个玩家席位独立于车型；换车及转场保持本次房间内的颜色／编号，Host占一席 |
| R2 | 允许取消确认 | 开始前可返回选车；取消后撤销开始资格，清理旧车球权／作用域状态并退出驾驶，再重新确认与出生 |
| R3 | 不额外设置准备按钮 | “确认车辆”同时表示同意Host开始；确认成功后可练习。内部仍检查车辆、ASC及必要客户端状态是否就绪，不把确认点击当作出生完成 |
| R4 | 练习不扣血 | 保留碰撞、控球、发射、冲击、脱球及技能，不开始正式比赛计时／淘汰；禁止HP扣减不能导致命中消费或独立冲击结算一起被跳过 |
| R5 | 展示配置四人，开发配置允许一人完整流程 | 最多四人含Host；展示开局要求四名参与者，开发至少一人即可选车、练习、转场、载入、倒计时与进入正式游戏；配置由服务器决定，不由PIE的Number of Players决定 |
| R6 | 开始前允许加入；开始后拒绝；Host离开全员回入口 | 服务器成功接受开始请求时锁定名单并关闭加入／改车；无效开始请求不锁房。Client退出清席位，Host退出时其他玩家回本地入口并显示原因 |

R3中的玩家确认、运行时就绪和既有DA的Ready For Use是不同条件，不新增第二个“准备”按钮，也不取消原配置有效性检查。

## 2. 流程与实现边界

本地街机入口 → 创建／加入房间 → 各自选车并确认 → 各自进入练习 → Host开始并锁定参与名单 → 服务器统一转场 → 全员载入就绪 → 同步倒计时 → 正式游戏。

选车与练习共用一个联机房间地图：确认者先练习，后来加入或未确认者继续选车，不必等全员一起切地图。先复用当前Host／IPv4 Join；原NetTest继续作为回归入口，新房间建议由团队手工复制测试地图并配置专用GameMode。正式地图与房间地图走明确可配置的引用，即使首版地形相同也要实际验证不同World的转场。

以下为本期实现默认／工程边界，不追加为用户逐项确认的玩法规则：

- 首版正式目标地图使用配置默认值，不制作地图投票或匹配服务；车型／地图引用须进入打包资源集合。
- 进入正式关卡按新一局初始化：满血、正确车型属性、技能可用；清除练习Buff／Debuff和冷却、球权、运动历史及相机／HUD旧引用。使用明确的新局入口，不在任意OnRep／重复Possess时自动回血或清效果。
- 房间／正式关卡按需建立专用C++ GameMode与GameState，复用PlayerState／ASC及窄职责组件；Widget不决定权威状态，不新建万能流程框架。
- 服务器统一ServerTravel并优先验证Seamless Travel；身份／车型显式保留或复制，车辆与球重新生成。无缝转场不等于状态自动正确或没有载入等待。
- 载入超时及失败必须有有界恢复：仍连接且可统一恢复时返回房间重新确认，不能恢复连接者回入口并说明原因。实际超时参数与恢复分支在GF-4施工规格中记录，不无限等待／无限重试。
- 本期不建设重连、主机迁移、完整淘汰／观战／胜负／结算。预留返回房间和开发结束入口，以验证连续两次开局；正式结算触发器以后接入。

## 4. 每环节具体施工与验收

### GF-1：数据与权限基础

- 增加小型车型目录：稳定VehicleId→车辆BP及显示元数据，BP继续引用原VehicleDefinition，不复制整套调参。只接受服务器目录中的ID，不接客户端任意类／资产路径。展示名、图标和预览与驾驶配置有效性分开。
- PlayerState保存服务器分配的席位／颜色／编号、选车与确认；GameState复制公共房间阶段、参与名单及本次开局标识。GameInstance保留本地UI／连接职责，不替代复制的房间状态。
- 分开房间公共阶段和每位玩家选车／出生状态；内部运行时就绪由实际初始化决定。采用少量语义清楚的权限查询，逐一梳理技能、相机、自救、机关和伤害的Playing硬判断。
- 明确练习允许驾驶／技能、禁止HP伤害；载入及倒计时禁止主动驾驶／技能／球权争夺及危险机关结算，观看与物理稳定过程按实现需要保留。UI禁用按钮不能代替服务器及物理输入权限。
- 展示／开发配置显式选择，不根据PIE或是否打包隐式改变。开发单人须覆盖Standalone及一名玩家的Listen流程，不为凑人数创建假玩家。
- 验收重点：目录重复ID／无效配置拒绝、人数及席位边界、阶段权限矩阵、请求只能作用于本人的选车状态、旧最小NetTest行为不被提前替换。交付GF-1详细说明与必要自动化；无需精细UI或跨图代码。

### GF-2：GAS与Avatar生命周期

- 现有InitializeHealth／Combat／Impact存在一次初始化保护；新增有语义的服务器换车型／新局初始化入口，普通重复绑定继续幂等，不粗暴清零全部初始化标志。
- 按授予来源移除旧车技能，清理旧Avatar作用域效果／冷却、区域贡献、冲击／自救／输入缓存，释放旧球权与约束，再初始化新车型种子与Avatar；共享玩家能力保留或重授予须有明确来源和去重策略。
- 练习不扣血通过统一战斗策略实现，独立保留冲击、脱球、命中状态消费和所需反馈；不通过永久免疫GE或在碰撞回调中硬改HP实现。
- 验收：两套明显不同的临时有效配置执行A→B→A，HP／攻击／冲击／移动来源正确，重复Possess／OnRep不回血、不重复授予；旧技能和区域效果不串车。重复调用同次新局重置不重复触发。生产DA测试参数由团队保存，代理仅用测试夹具不覆盖原资产。

### GF-3：灰盒房间、选车与练习

- 连接成功先占席位并显示选车；确认后服务器验证车型、配置和出生点，生成车辆并Possess，真实完成初始化后才能开始资格成立。
- 已确认者练习，其他人继续选择；任何玩家都可选同车型。基本UI显示四席位、颜色／编号、车型、确认／出生中／失败状态与Host开始条件。
- 取消确认先撤销资格再清理旧Avatar，返回选车；出错保留可重试状态，不把没有车辆当作准备完成。
- 开始前允许加入，开始请求只有Host有效；按当前配置检查全部参与者确认及运行时就绪。同帧确认／取消／加入／开始由服务器状态决定，反复点击不生成多辆车。
- 基本离房与Host退出回入口同段接入，清理球权、旧UI、IMC和焦点。蓝图／Widget／地图／颜色素材由团队按逐步Editor说明手动接线。
- 验收：开发单人、真实双端同／异车型、取消重选、晚加入、配置无效／出生阻挡、反复提交、Host／Client退出；练习HP不变且冲击及技能可用。此段不冒充已经可以跨图开赛。

### GF-4：真实跨图与全员开赛

- 成功开始时原子地锁定名单、车型与开局标识，并关闭加入／取消。拒绝的请求不改变房间；保存状态不依赖旧Pawn指针或GameState跨图存活。
- 先跑通服务器到目标地图的真实转场，再处理身份／选车保留、正式出生及ASC绑定。正式场不继承练习球、速度、Buff、冷却或旧输入历史。
- 载入确认绑定本次开局及本人，由服务器结合目标World、有效Avatar／ASC检查；不能凭任意Client“Ready”或固定延时判定全员就绪。
- 全员就绪才设置共同服务器倒计时结束时刻；结束前权限不开放。慢机、载入失败、过程中断线、Host离开和超时均走明确恢复分支，不在失败后悄悄改为少人展示局。
- 验收：一人Standalone／Listen完整走通；两台独立进程／电脑真实跨图，慢载入模拟、重复／过期消息、名单锁定后加入拒绝、清理与倒计时一致。团队手工创建／复制目标关卡及必要Transition Map配置，保留原回归地图。

### GF-5：入口与表现

- 街机待机页到Host／Join，选车确认到练习，加载到倒计时完整可操作；兼容手柄优先与键鼠，明确输入焦点、光标、取消返回和驾驶切换。
- 四人颜色／编号贯穿房间、车辆标识与HUD；车型预览不参与物理，不影响服务器出生类。素材引用可替换，缺少图标／预览时有占位显示。
- 加入失败、房满、比赛已开始、车型不可用、出生失败、载入超时均提供可读反馈及下一步操作；不把内部编译／复制细节放进玩家流程。
- 验收以实际窗口／手柄和画面为准，自动化数据通过不能替代UI接线与可读性实测。

### GF-6：闭环与四机

- 通过开发结束入口返回房间，保留车型偏好但重置确认，允许重新选车；它只验证生命周期，不等同于正式胜负／结算系统。
- 同一房间连续两次选车、练习、开赛与返回，第二局使用新开局标识；无旧Buff、技能、球、预测缓存、HUD／相机目标残留。
- 打包核对两类车辆、引用DA、房间／正式／过渡地图及UI资源，不能仅凭Editor能加载推定发布包齐全。
- 四台真实电脑同一有线网络，记录提交、构建／引擎补丁、Host身份和各端结果；验证展示四人门槛、同车型归属、全员跨图、慢机与退出、Host断开全员回入口，并保留日志和视频。GF本期流程验收与原球／VP／F4欠项分别记账，不以一项通过替代另一项。
